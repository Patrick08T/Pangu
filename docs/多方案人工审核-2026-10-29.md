# 多方案人工审核

## 使用方式

审批事项存在多个真实可行方案时，报告提供方案名称、影响和取舍，并标注推荐项及理由。互斥方案使用单选，可组合方案使用多选。推荐项不预先勾选，必须由审核人明确选择。

- 所选方案与当前计划相同：所有审核项通过后，可以批准执行。
- 所选方案改变当前计划：自动视为纠偏，提交后由相关角色修订计划，再进入下一轮人工审核；选择本身不授权实施。
- 方案都不合适：可清除方案选择，仅填写文本纠偏意见。
- 人工审核持续等待，不自动过期；历史记录保留本轮方案、推荐依据和实际选择。

现有运行冻结的报告与版本保持原样。新发布的工作流和新生成的交付审核计划使用新格式；旧报告没有提供备选方案时，界面不凭空生成选项。

## 数据格式

审核项保留原有字段，存在多方案时增加以下字段：

```json
{
  "id": "scope",
  "category": "范围",
  "title": "本轮交付范围",
  "proposal": "先验证需求，再进入实现",
  "rationale": "方向尚需验证",
  "task_ids": [],
  "evidence_refs": [],
  "selection_mode": "single",
  "options": [
    {"id": "research", "label": "先验证需求", "description": "投入较低，但功能上线更晚"},
    {"id": "prototype", "label": "同时开发原型", "description": "更快验证使用体验，但开发投入较高"}
  ],
  "recommended_option_ids": ["research"],
  "planned_option_ids": ["research"],
  "recommendation_reason": "当前方向不确定性较高，优先减少无效开发"
}
```

`selection_mode` 为 `single` 或 `multiple`；每项提供 2 至 6 个不同方案。推荐集合必须非空，当前计划尚未确定时 `planned_option_ids` 可为空。单选的推荐及当前计划最多包含一个方案。每个引用必须属于本项方案列表，重复及未知标识均拒绝。

审核人选择原型后，提交的逐项答案为：

```json
{
  "item_id": "scope",
  "decision": "revise",
  "correction": "",
  "selected_option_ids": ["prototype"]
}
```

整体决定必须为 `changes_requested`。已有明确方案选择时，不强制重复输入同义文本。后端拒绝使用 `accept` 或 `approved` 绕过计划修订；空选择不能批准多方案审核项。

修订角色通过 `review_feedback.items.selected_option_ids` 和 `previous_review` 读取选择及原始语义，修订计划、任务和依赖，并逐项回应。多选集合顺序不影响同一审核决定的幂等重试。下一轮审核重新绑定完整报告及检查点，不沿用上次批准。

## 实现边界

新增字段使用现有审核快照和决定 JSON 保存，无需数据库迁移。采用平铺字段，完整报告结构仍满足现有深度限制。没有真实备选方案的审核项继续采用同意、需调整、不接受，不为了凑选项而生成虚假方案。

模型提示词、共享市场迭代模板、交付审核计划和工厂生成指令均说明方案及推荐规则。工厂对话提示模型列出备选项；正式工作流审批页依据结构化报告渲染单选或多选。
