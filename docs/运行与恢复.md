# Windows 安装、启停、升级与恢复

首版是单机、固定 Worker 磁盘的部署。Pangu API 只监听 `127.0.0.1`。正式网络入口、TLS、飞书应用和模型凭据由部署管理员配置。没有登录配置时健康检查和登录入口可访问，项目业务不会匿名放行。

## 安装包

构建机需 Go、Node 24、Git、Rust stable/MSVC，以及固定版本 Hatchet sidecar。先用 `scripts/codex-build.ps1` 构建受控 Codex，再执行：

```powershell
powershell -NoProfile -File scripts/check.ps1 -Database
powershell -NoProfile -File scripts/package.ps1 -Destination C:/packages/pangu-windows-amd64.zip
```

安装包包括嵌入前端的 `pangu.exe`、`database.exe`、Hatchet sidecar、受控 Codex、脚本、接口契约、示例与中文文档。包内不放数据库数据、登录文件或本机凭据。`构建依赖.txt` 保留 Go 二进制依赖，`licenses` 收集依赖自带的许可证和声明；Codex 清单标出没有随 crate 提供许可证正文的依赖，附带其来源和原始元数据，不能将材料收集视为完整法律审计。目标 ZIP 必须不存在，打包后校验关键文件和禁止分发的配置文件。

运行机器无需 Node、Go 或 Rust；仍需 Git、模型服务及飞书应用。Hatchet 首次启动会下载匹配的 PostgreSQL 运行库，需要网络；已有 `.tools/hatchet-postgres` 时使用本地数据。受控 Codex 位于 `.tools/codex/codex.exe`，不替换系统安装，不带登录信息。解压到管理员选定目录，不放进 Agent 项目仓库或公共共享目录。

## 首次配置

所有命令在安装目录执行。`.env.example` 是环境变量说明，程序不会自动加载 `.env`。使用管理员选定的启动环境注入凭据，不把 Secret 写进聊天、Git 或命令日志。

```powershell
powershell -NoProfile -File scripts/hatchet.ps1 -Background
# 等待 .tools/hatchet-connection.json 生成，再创建产品数据库。
$state = Get-Content .tools/hatchet-postgres/data/postmaster.pid
$databasePort = [int]$state[3]
$env:PANGU_DATABASE_ADMIN_URL = "postgresql://postgres:postgres@127.0.0.1:$databasePort/postgres?sslmode=disable"
try { & ./scripts/database-init.ps1 } finally { $env:PANGU_DATABASE_ADMIN_URL = $null }
```

上例超级用户凭据仅对应上游嵌入式本地 PostgreSQL 默认值；产品服务使用随机密码的独立 `pangu_app` 账号。外置 PostgreSQL 按本机实际管理连接配置，不能套用默认值。`.tools/pangu-database.json` 和 `.tools/hatchet-connection.json` 含凭据，必须限制目录访问。测试使用 `database-init.ps1 -TestDatabase` 建立独立库；不得让测试连接产品库。

按 [飞书与项目权限](飞书与项目权限.md) 配置应用、允许租户、首位管理员和回调。`PANGU_PUBLIC_URL` 必须等于浏览器实际来源；本地默认 `http://127.0.0.1:8081`。模型连接需要服务端环境凭据和项目/端点授权登记。

原生 Codex 使用独立的 `PANGU_CODEX_HOME` 目录，启动脚本默认 `.tools/codex-home`。管理员在这一目录对应的 `CODEX_HOME` 下完成登录，并在其中的 `config.toml` 显式登记技能、MCP、外部地址及依赖。Pangu 只向子进程传入必需环境；项目配置不受信任，自动技能发现/安装、插件、子 Agent 和托管搜索关闭。受控构建在原生执行前检查次数与时限，普通 CLI 不满足能力探测会被拒绝；详见 [构建与限制](../runtime/codex/README.md)。

## 日常启动与停止

```powershell
powershell -NoProfile -File scripts/start.ps1 -Port 8081 -Mode all
Invoke-WebRequest -UseBasicParsing http://127.0.0.1:8081/api/healthz
# readyz 需完成飞书配置并以已登录会话或有效 Token 查询。
powershell -NoProfile -File scripts/stop.ps1
powershell -NoProfile -File scripts/hatchet-stop.ps1
```

`start.ps1` 只启动本目录二进制，后台窗口隐藏；默认目录为 `.artifacts/workspaces` 和 `.artifacts/audit`。显式配置的目录优先。脚本恢复调用者环境，改变端口再次启动不会继承上次自动生成的 Public URL。服务进程已启动不代表模型就绪；运行前还需通过工作流诊断。`/api/readyz` 受身份认证保护；飞书未配置时返回 503 身份服务未配置，不能据此断言数据库损坏。

`stop.ps1` 校验 PID、可执行文件路径和进程创建时间后才停止，避免 PID 复用误杀。Windows 强制停进程会关闭其 Job 内子进程，Hatchet 保留在途任务供恢复；正常维护应先暂停计划、停止提交并等待运行结束。Hatchet 停止脚本发送宿主关闭信号后，必须等待 `postmaster.pid` 消失才能备份。不要手工删除该文件来绕过检查。

引擎日志位于 `.artifacts/hatchet.stderr.log`，Pangu 日志位于 `.artifacts/pangu.stderr.log`。嵌入式连接池每池最多 10 个普通连接、2 个 DDL 连接，避免多个引擎组件耗尽默认 100 连接的 PostgreSQL。Hatchet 自己的 CLI profile 保存在本实例 `.tools/hatchet-home` 下。

## 每日与升级前冷备份

Pangu 采用 PostgreSQL 官方支持的停机文件备份，两个库、Hatchet 密钥和工作区一起复制。备份前暂停所有计划、停止新提交、等待活动运行终结；停止本机所有 Pangu 进程（包括 `go run`）、本实例 Hatchet 和 PostgreSQL。跨实例共用磁盘、仍有活动运行或文件正在变化时不能做此演练。

```powershell
powershell -NoProfile -File scripts/backup.ps1 `
  -WorkspaceRoot C:/PanguData/workspaces -AuditRoot C:/PanguData/audit `
  -Destination D:/PanguBackup/2026-10-24
```

必须传入本次实际目录。脚本拒绝活动库、运行中的 Pangu、已有目标、目录重叠和 junction/symlink；私有备份目录仅授权当前用户及 SYSTEM。SHA-256 清单覆盖每个文件，备份末尾再次确认数据库未启动。失败的目录不是有效备份，修复原因后使用新目标重做。

备份包含产品数据库凭据、Hatchet 管理员密码和数据库内密钥，目录 ACL 不等于磁盘加密；异机存放应使用管理员的加密介质。飞书、模型和 Codex 登录凭据由管理员独立备份，脚本不会扫描个人目录收集密钥。每天由管理员执行，首版不自动注册 Windows 定时任务或开机服务。

## 恢复与升级回退

```powershell
powershell -NoProfile -File scripts/restore.ps1 `
  -Backup D:/PanguBackup/2026-10-24 -Destination C:/PanguRestore
```

恢复要求全新目录，先验证全部清单、路径、摘要和文件长度，再复制。脚本不覆盖原实例、不启动 Worker。把匹配版本安装包的程序、脚本和文档解压到恢复目录，保留恢复出的 `.tools` 数据和凭据。先以原版本启动 Hatchet，再运行产品迁移/检查；升级只允许向前迁移，回退必须切换完整备份，不能把旧程序指向升级后的数据。

更换绝对路径时，工作区记录仍指向原路径。最稳妥的生产恢复是在原路径停机还原。独立演练应保留原实例，并只对副本产品库的 `workspace_runs.directory` 做旧工作区根到新工作区根的精确替换；先检查每条路径严格位于旧根、Worker 身份相同，再逐条更新。项目 `source` 也需要管理员重新登记正确位置，历史固定基准仍由保存的 clone 读取。不要直接修改 Hatchet 内部表。

副本可用 `hatchet.ps1 -Background -GRPCPort 17071 -APIPort 28244` 与原实例并存；读取副本 `postmaster.pid` 获取新 PG 端口。先启动 API 查询历史，确认无问题后再启动 Worker；副本的旧 Cron 不能在未检查的情况下连接真实模型。两实例不得共用工作区目录、数据库或同一个 `PANGU_WORKER_ID` 执行任务。
