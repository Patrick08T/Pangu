# 结构化人工审核使用与验证

日期：2026-10-29。

## 审核方式

打开 [人工审核中心](http://127.0.0.1:8081/#/approvals)，选择当前项目，在“等待审核”中打开一条记录。运行详情也提供审核入口。

每项选择“同意”“需调整”或“不接受”，默认均未选择。输入纠偏文本会自动选择“需调整”。可以仅提交部分项目的意见，其他项目保持未决定。整体调整写在页面底部。

- **全部同意并批准执行**：须全部明确同意，且没有纠偏文本或上一轮未解决意见。批准绑定本轮计划、完整报告及 Git 检查点。
- **提交纠偏，修订后复审**：只读规划角色按依赖顺序重新修订，各角色报告与统一计划同时更新，然后创建下一轮审核。查看原建议、人工意见、新建议和处理说明，再重新确认。
- **驳回并结束**：填写整体原因后终止工作流。“不接受”单项提议只进入修订，不等同于结束整个流程。

审批无自动过期时间。页面关闭、离开或 Worker 重启不会自动批准。网络结果不明时，表单锁定，只允许重试同一决定；状态冲突需重新读取。运行结束或正在取消时，记录只读。

历史过期运行不会复活。旧运行 `733b1cd1-704a-4c67-964b-c12ecf109d04` 仍是历史记录，不能在该记录上补做审批。

## 报告与工作流约定

完整格式见 [已确认设计](superpowers/specs/2026-10-29-结构化人工审核设计.md) 及 [运行契约](../specs/运行契约.md)。审批节点配置示例：

```json
{
  "source_node": "execution_plan",
  "revision_nodes": ["direction_roadmap", "plan_development", "plan_quality", "plan_performance", "plan_security", "plan_operations", "plan_acceptance", "execution_plan"]
}
```

审核项直接读取汇总报告的 `review` 对象，依据使用同一报告内的 JSON Pointer，例如 `#/evidence/0`；任务引用必须存在于报告 `tasks`。整体纠偏回应使用保留 ID `overall`。审核项最多 200 项，单项纠偏及整体意见最多 4000 字符，决定请求不超过 1 MiB。

修订只运行已配置的规划节点，保留已有研究。需要额外研究时须说明未解决证据缺口，不会由意见文本自行增加联网节点。配置了调用预算时，修订同样扣减原预算；预算不足会失败，不会使用旧计划继续实施。

旧工作流必须补齐配置与报告结构后发布新版本。没有根据旧自然语言报告自动猜测审核项的兼容路径。

## OCR 审查

实际执行 `ocr delegate preview` 与 `ocr delegate rule`，由当前主代理依照 OCR 返回的 Go、React 及通用规则完成审查；没有调用外部模型或宣称独立审查。原始输出保存在 `.artifacts/structured-review-ocr-preview.json`、`.artifacts/structured-review-ocr-rules.json`。

审查发现并已修复：

1. 修订时查询可能回退到上一轮成功报告：改为仅使用最新逻辑节点尝试，新增失败再通过测试。
2. 已完成旁支或同层节点可能继续持有旧计划：审批独占一层，检查已完成受影响节点的修订闭包，新增失败再通过测试。
3. 参数绑定在审批冻结前后不一致：冻结前重新绑定当前输出，真实 Hatchet 测试覆盖绑定字段。
4. 实施角色可能优先读取原始输入的旧任务：明确传递本轮已批准计划为实施范围，原始需求不恢复已移除任务；模拟 Codex 进程验证实际提示与新版报告。
