# 结构化人工审核与纠偏复审

日期：2026-10-29。状态：用户已确认，代码已实现；实际验证及部署记录见《结构化人工审核使用与验证-2026-10-29》。

## 已确认需求

- 设置专门的人工审核界面。
- 使用独立、可验证的数据格式，逐项呈现需要用户决定的问题。
- 每项可以选择审核结论，并输入文本纠偏。
- 用户已选择：提交纠偏后修订计划，再次人工审批。
- 用户已选择：采用 TDD，先写失败测试再实现。
- 审批不自动过期；等待期间暂停实施，最终批准后继续工作流。

## 现状与问题

当前 `web/src/approval/workflow.tsx` 将全文报告和一个总决定表单嵌在运行详情中。后端 `approval.Decision` 仅有 `subject_hash`、`decision`、`reason`，数据库每个运行节点只能创建一条审批。调度器等待持久审批事件后，批准则执行，其他决定使运行失败。

已有能力可以复用：身份与项目权限、CSRF、固定输入与报告正文哈希、Git 检查点核验、审批事件投递、执行前批准消费、运行取消、只读规划角色、报告存储以及现有前端组件。

纠偏不能只改变页面展示或给实施节点追加一句话。当前下游除统一计划外，还直接引用各角色报告；修订必须更新相关报告及统一计划，并让后续节点使用这一轮一致的产物。

## 方案选择

推荐在同一运行内增加多轮审批与只读修订阶段。保留已完成研究，按固定配置重跑规划角色并汇总计划；每轮生成新的冻结审批内容，实施继续等待。这样无需让用户重新启动整条工作流，也不依赖目前仅支持部分场景的检查点返工。

另一条可行路径是把每轮修订做成新运行，再把批准结果接回原运行。它需要额外的跨运行权限、取消、产物继承与状态协调；本次不采用。

本次不扩展为通用循环编排系统，不增加多人会签、提醒通知、代理审批或自动批准。

## 页面与操作

主导航新增“人工审核”，列表位于 `#/approvals`，按当前项目列出待审核、修订中和历史记录。列表显示任务名称、节点、当前轮次、状态、创建时间及已提交结果，不返回或渲染全部报告正文。

详情位于 `#/approvals/{id}`，运行详情保留状态摘要及“打开审核”入口。详情分为任务概览、审核项、纠偏处理记录、历史轮次及来源材料；完整报告作为可展开的依据，正常操作不需要阅读 JSON。

每个审核项呈现：

1. 标题、待决定的具体建议和理由。
2. 所属分组、相关任务，以及可打开的依据。
3. 未默认选中的三个选项：同意、需调整、不接受。
4. 独立的纠偏文本框；需调整或不接受时必须填写。

“不接受”表示该项提议需要重新处理，不自动终止整个工作流。结束整个工作流使用单独的“驳回并结束”按钮并填写原因。

底部显示未处理项和纠偏项数量，提供“全部同意并批准执行”“提交纠偏，修订后复审”“驳回并结束”。全部同意要求每项都有明确选择，且没有纠偏文本；输入纠偏会将该项改为需调整，不能以批准附言方式绕过复审。提交纠偏允许其他项目尚未决定，其未决定状态原样传递，不能视为同意。

新一轮显示前后建议、用户意见和角色处理说明；所有项目重新确认，不继承上一轮的批准选项。表单未提交时导航离开有提示；本次不增加服务端草稿或跨设备表单同步。

## 专用数据格式

规划报告增加标准 `review` 对象，由平台校验后冻结到审批主体。数据由负责汇总的规划角色生成，不从自然语言段落自动猜测审核项。

示例：

```json
{
  "review": {
    "title": "Pangu 本轮方向与执行计划",
    "summary": "确认方向、范围、任务、验收及停止条件。",
    "items": [
      {
        "id": "direction",
        "category": "产品方向",
        "title": "是否保留研发工作流方向",
        "proposal": "保留研发工作流方向，本轮聚焦研究到交付的证据连续性。",
        "rationale": "现有能力已覆盖执行链，整体转向的需求证据不足。",
        "evidence_refs": ["#/evidence/0"],
        "task_ids": ["MR28-PM-01"]
      }
    ],
    "resolutions": []
  }
}
```

`resolutions` 在首轮为空；后续逐条填写 `item_id`、`status`、`explanation`，状态为 `addressed` 或 `unresolved`。整体纠偏使用保留 ID `overall`，审核项不能使用该 ID。它表示角色如何回应用户意见，不表示用户已同意。被移除的项目保留其处理记录；未解决的纠偏阻止整体批准。上例省略报告中的 `tasks` 和 `evidence`；实际引用必须能定位到同一报告的内容。

用户提交的数据与模型建议分开存储：

```json
{
  "subject_hash": "页面所对应的冻结内容摘要",
  "decision": "changes_requested",
  "reason": "先收窄本轮范围。",
  "items": [
    {
      "item_id": "direction",
      "decision": "revise",
      "correction": "请把目标用户收窄为独立开发者，并说明相对手动 Codex 的价值。"
    }
  ]
}
```

项目结论限定为 `accept`、`revise`、`reject`；缺少的项目保持未决定。整体决定包括 `approved`、`changes_requested`、`rejected` 和已有的执行前 `revoked`。

平台校验项目 ID 唯一、字段非空、引用与任务 ID 有效、意见长度与载荷大小、未知字段和敏感内容。建议初始限制为最多 200 项、单项纠偏最多 4000 字符，整体提交不超过 1 MiB；这些是输入格式限制，不是审批等待或模型执行期限。

批准必须覆盖本轮全部审核项，且全部为 `accept`、纠偏文本为空、没有未解决的修订意见。服务端执行同样校验，不能仅依靠按钮禁用。

## 工作流配置与修订

审批配置明确审核报告来源节点和修订节点集合。报告来源必须是直接上游；修订节点必须属于已完成的上游规划范围，并具有只读执行约束。来源字段固定为报告的 `review`，不引入任意脚本表达式。

审批前校验配置及标准报告格式，缺失时报告具体字段问题，不能把整份原始 JSON 默认为用户已经逐项核对。

市场迭代流程的修订集合为：

`direction_roadmap → plan_development → plan_quality → plan_performance → plan_security → plan_operations → plan_acceptance → execution_plan`

保留 `product_context` 和 `market_research` 的已完成报告。本轮按现有依赖顺序重新规划，避免某一角色的任务调整后其他角色仍引用旧任务。若纠偏需要新的联网研究，规划报告须说明证据缺口；本次不会因意见文本自行派生新的研究节点。

只读修订接收上一轮计划、完整逐项决定和纠偏文本。意见来自经身份核验的人工提交，并携带审批 ID 和轮次；网页或模型报告不能伪造这个来源。

修订产物更新运行中的有效节点输出集合，再重新构建审批节点及后续节点输入。新计划和旧角色报告混用必须被测试覆盖并阻止。

## 状态、持久化与恢复

每轮独立保存审批记录，增加轮次及上一轮关联。数据库唯一性改为 `(run_id, node_id, round)`；旧记录作为第 1 轮保留，原始正文、摘要和人工决定不改写。

正常路径：

`待审批 → 逐项同意并提交 → 批准 → 执行前复核 → 实施`

纠偏路径：

`待审批 → 提交纠偏 → 只读修订 → 新轮次待审批 → 人工复审`

运行层面显示“待审批”或“计划修订中”，修订期间实施节点仍未放行。旧轮次标记为已请求修订，保留其全部意见，并链接下一轮。修订失败显示实际失败节点和原因，不恢复旧批准、不伪造新计划、不继续实施。

每轮等待无过期时间；取消优先于修订派发和批准消费。Worker 重启重放必须复用已生成的轮次、已完成的修订节点和审批事件，不重复派发模型或产生第二份审批。用户再次提交纠偏才允许开始下一轮，不设置隐式自动修订循环。

现有子任务查询有固定 33 条上限，多轮修订会超过它；实施时改为分页获取直接子任务。运行视图保留历史尝试，并明确每个节点当前有效版本，不能把旧成功结果误认作本轮修订完成。

## 权限、绑定与历史数据

复用当前项目管理者、运行创建者与操作者规则；审核只能通过当前允许的人工登录身份，API token 不获得审批权限。列表、详情和历史轮次都校验项目可见性。

每轮批准绑定该轮审核项、完整报告、输入和 Git 检查点。报告变化、旧页面提交、重复项目、缺项、越权及取消竞态均拒绝。相同提交重试保持幂等，内容不同的重复提交返回冲突并要求重新读取。

已有失败或过期审批保留历史只读展示，不自动复活。旧工作流需要补齐新审批配置和报告格式后发布新版本；不增加猜测旧文本审核项的兼容路径。升级前必须确认没有活动的旧格式待审批运行；如存在则先保留原服务处理，不通过迁移取消它们。

数据保留与清理同步覆盖新增的审核项和意见。列表不得泄露跨项目内容；前端以普通文本呈现模型及人工文本，不执行其中的 HTML 或脚本。

## TDD 与验收

先写并运行失败测试，再实现对应行为：

1. 无默认选择；缺项不能批准；逐项纠偏和总意见原样提交；未解决意见不能放行。
2. 页面离开提示、键盘操作、错误定位、并发冲突及网络结果不明时的幂等重试。
3. 服务端拒绝未知项目、重复项目、伪造来源、过期轮次、跨项目访问、越权和敏感文本。
4. 提交纠偏后实施调用数为零；修订角色实际收到意见；新轮次展示修订产物并等待复审。
5. 批准新版后只执行一次，后续节点引用新版统一计划及角色报告。
6. Worker 在等待及修订途中重启，轮次、事件与节点结果不重复；取消和撤回仍生效。
7. 超过 33 条子任务仍完整显示；修订失败不得回退到旧批准或旧计划继续实施。
8. 数据迁移保留历史正文和决定，历史审批不可操作；清理逻辑覆盖新增数据。

完成针对性测试、契约生成、类型检查、构建及架构检查后执行实际 OCR 审查并保存输出。使用真实 Hatchet 配合模拟模型验证审批与修订流程；真实模型生成质量另行报告，不能以模拟测试宣称已验证。

## 交付边界

本次开发不代表批准 MR28-01 或启动产品实施。旧运行 `733b1cd1-704a-4c67-964b-c12ecf109d04` 的历史失效记录不会自动变成可审批的新轮次。

完成开发后应明确报告本机是否部署、新版工作流是否发布，以及真实运行是否已启动；不能把代码完成写成页面已经可用。涉及数据库结构变化时，部署前保留审批相关数据和程序备份，并说明回退所需的数据恢复步骤。
