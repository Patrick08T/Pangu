# 工作流循环块

## 已确认的行为

保留发现、复现、修复、自测、OCR 审查、QA 六个独立 Agent。自测、审查或 QA 任一未通过，保留当前代码与证据，从发现步骤进入下一轮；同一轮、同一份代码的全部质量检查通过后才完成。不设默认轮数上限。取消、已有调用预算和权限约束继续生效。

## 数据和执行边界

工作流增加 `loops`，每块声明稳定 `id`、成员 `nodes` 和按执行顺序排列的 `gates`。外层依赖图仍无环，块内也是无环图，平台控制重复执行。循环块不能重叠或嵌套。块内使用独立 Codex 节点，不混入人工审批、条件跳过或研究角色；人工决策放在块外。修复阶段允许并行依赖，质量门按顺序运行，所有修改步骤必须完成后才进入质量门。块外下游只能从最后质量门取结果。

质量门为只读节点，输出含必填 `passed:boolean` 和 `summary:string` 的结构化对象。`passed:false` 是正常的检查结论，触发返修；输出不合法、模型、权限、工具启动等执行异常沿用已有错误/重试机制，不伪装成业务不通过。质量门不得修改文件，平台核对代码树摘要，不能拿上一轮结果满足当前验收。

每个派生任务带循环 ID、轮次及上轮失败节点、摘要、原始运行/报告引用。仅传递最近失败反馈，完整历程保存在现有尝试、日志、证据、检查点中，不累积塞入提示词。任务幂等键包含循环 ID 和轮次，模型重试有独立编号。Worker 恢复按持久任务重放，不重复执行已完成步骤。手动检查点续跑仅复用当前轮可验证的前缀，不能混入旧轮成功结果。

## 工作区与验证

每次修复从当前已发布检查点开始。循环内发现、复现、修复阶段不运行项目统一验收命令，允许红测试和待修补丁成为中间检查点。项目统一验收命令在质量门执行；明确的非零退出码转成不通过结论并保存证据，启动失败/取消仍是执行异常。块外原有节点行为不变。Git 与 Perforce 均复用现有快照机制，不提交到用户远端。

OCR 显式比较 `revision.origin_commit` 到 `revision.head_commit`，避免干净检查点产生空的默认审查范围。Perforce 的质量门额外获得 `review_repository` 外部快照路径，仅供 `ocr --repo` 和 `git -C diff/show` 读取；完整上下文读取指定提交，不依赖快照工作树。绑定的本地 P4 目录不会写入 `.git`。同层多个循环块目前依次执行；块内修改步骤仍按依赖并行。

## 配置和可观察性

工厂候选、发布版本、运行快照、OpenAPI 和编排页面均保留循环定义。编排页可选择成员和质量门；运行页区分循环轮次、模型重试、节点尝试，展示质量门结果和失败原因。工厂可直接生成六角色循环方案；历史会话与已发布版本保持原样，新消息使用新能力。

## 验证

按已获授权执行 TDD：先验证质量失败后返修、三门同轮同代码通过、恢复和取消/预算边界，再完成编排/工厂/页面接线。测试不得调用生产模型。最终执行项目函数长度和模块边界检查、前端构建以及 OCR 逐文件审查。
