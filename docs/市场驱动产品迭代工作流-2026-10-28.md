## 已确认的设计

使用固定角色节点和动态任务清单。产品、开发、QA、性能、安全、运维、验收七类角色协作，另由联网研究员提供原始市场证据。各角色先拆解任务，再由产品经理统一排程；不在运行中生成新的 Agent 或工作流图。

汇总的产品方向、路线图差异、任务清单、验收标准和写入范围只需人工确认一次。确认前原生执行节点全部只读；研究员使用平台限定的资料工具。只有确认后的实施阶段可以写入批准的产物。

本轮平台修复采用 TDD；Pangu 此次沿用 Git-only，不提交或推送。之后每次业务运行的测试策略和版本管理要求由运行输入及所选项目规范决定。

## 流程与产物

| 阶段 | 步骤 | 主要产物 |
| --- | --- | --- |
| 现状与研究 | 1–2 | 产品与路线图现状；有来源的竞品矩阵、差距、细分市场、反证和未知项 |
| 方向与任务 | 3–9 | 路线图保留、调整、推迟、取消、新增建议；七角色可执行任务 |
| 统一计划 | 10 | 去重后的任务依赖、责任人、阶段、范围、验证方法、资源及停止条件 |
| 人工确认 | 11 | 一次批准后写入中文方向决策、路线图和冻结任务/验收矩阵 |
| 执行与检查 | 12–17 | 测试资产、实现、适用性能验证、QA、安全和交付检查 |
| 修复与复验 | 18–22 | 一轮集中修复，随后 QA、性能、安全和最终交付复核 |
| 产品与验收 | 23–24 | 需求到证据的追溯、路线图实施状态、独立验收结论和下一轮建议 |

各节点串行运行以适配当前共享工作区检查点约束，任务依赖在统一计划中表达。安全和运维角色负责只读评审，必要防护、脚本与配置实现明确分配给开发。没有性能目标时允许不做优化，但需解释适用性。

研究不强制导致产品转向。证据支持原方向时保留原方向；证据不足时可选择最小验证型迭代，不能把竞品功能缺口直接当作已证实的用户需求。

## 运行输入

在运行入口选择项目与该工作流 v1，填写以下字段。所有文档路径须相对于项目，且在运行的基准快照中实际存在。

| 字段 | 填写内容 |
| --- | --- |
| `question`，必填 | 本轮要解决的产品问题与期望交付 |
| `context`，必填 | 产品定位、已有能力、当前路线图及路径、目标版本、反馈和本轮目标 |
| `constraints`，必填 | 可修改目录、隔离环境、资源约束、测试策略、验收标准与停止条件 |
| `audience` / `market` / `time_scope` | 目标用户、地区/市场、资料时间范围 |
| `public_queries` | 允许向公开搜索服务发送的完整查询词 |
| `urls` | 授权读取的公开网址 |
| `documents` | 授权读取的项目资料相对路径 |
| `competitors` / `dimensions` | 候选竞品及比较维度 |

`public_queries`、`urls`、`documents` 至少填写一种；仅填写竞品名称不会启用联网研究。若需要市场上的最新资料，请提供公开查询词或网址。每个列表最多 10 项，每项不超过 2048 字节；每项背景文本不超过 16 KiB。搜索词不能包含私密产品资料。

以下为填写格式示例，替换占位内容和真实存在的资料路径后使用：

```json
{
  "question": "对比同品类产品，评审当前路线图，交付一个经确认的最小完整迭代",
  "audience": "填写目标用户及核心使用场景",
  "market": "填写目标市场和地区",
  "time_scope": "填写资料时间范围",
  "context": "填写产品定位、当前能力、路线图路径、目标版本和用户反馈",
  "constraints": "填写可修改目录、隔离验证环境、测试策略、资源上限、验收与停止条件；完整计划由我确认后实施",
  "public_queries": ["填写允许公开发送的同品类产品查询"],
  "urls": [],
  "documents": [],
  "competitors": [],
  "dimensions": ["核心任务与体验", "功能和限制", "商业模式", "切换成本"]
}
```

请核对运行选用的提交快照。工作目录中尚未纳入快照的改动不会自动成为研究和实现基线；本次创建工作流没有提交现有改动。

## 审批与完成判定

唯一审批位于 `apply_plan` 前，等待窗口为 3600 秒。平台绑定本轮输入、上游执行计划与当前检查点，批准后才写入路线图并实施。批准前请核对范围、方向、任务依赖、写入目录、测试策略和验收标准。

- `execution_plan.ready=false` 时不进入审批和实施；缺口保留在计划结果中，补齐输入后重新运行。
- QA 等检查报告的 `ready=false` 是修复输入，不会仅因该布尔值跳过集中修复和后续复验。
- 上述修复路径处理正常返回的缺陷报告。工具异常、无效输出或运行失败仍遵循平台失败处理，不保证自动恢复。
- 集中修复只执行一次，不扩大已批准范围；复验仍有关键问题时最终验收不得通过。
- 只有最后的 `acceptance` 节点可以输出 `iteration_complete=true`。任务状态显示 `succeeded` 只代表编排运行完成，不能替代业务验收结论。
- 产品复核发生在最终验收前，因此路线图中的实施状态不会被提前标为正式验收完成；最终验收报告是本轮完成依据。
- 不自动提交、推送、部署或发送外部消息。市场采纳、上线效果和商业收益需后续观察，不能通过本地测试宣称已证实。

节点任务清单使用稳定 ID，包含负责人、执行阶段、前置依赖、范围、交付物、验收、验证方式及状态。非研究节点的输出保持在 12 KiB 内，详细产物放在已授权文件中并引用路径。

## 报告正文交接修复

原生 Codex 下游原先只能取得研究报告标题和 ID。本次在执行前从原始数据库读取直接上游报告正文，附在该父节点的执行上下文中，保留报告身份，不修改持久节点结果或审批摘要，不缓存报告。

读取同时校验当前运行、上游节点、报告 ID、所属项目和工作区有效性；拒绝敏感凭据、非直接上游及超过 1 MiB 的完整执行输入。超限明确失败，不截断证据。报告内容标记为资料，不作为新增指令或授权。

修复已构建并部署到本地 Pangu。重启前没有在途运行和定时任务，数据库与 Hatchet 保持运行。原程序备份位于 `.artifacts/market-iteration-before/pangu.exe`。
